Trust surface

Documentation still missing

For a researcher-facing tool, documentation is part of correctness. People need to know what leaves their machine, what is probabilistic, what can be reviewed, and what claims the outputs can support.

Before v0.1.0

Essential

  • Data handling & privacy. State that Markdown content is sent to Gemini; reference titles may be sent to CrossRef/OpenAlex; explain API-key storage and the implications for unpublished/confidential papers.
  • Accuracy & limitations. Explain LLM extraction errors, OCR failure modes, fuzzy-dedup false merges/splits, author ambiguity, language/layout limitations, and the need for human verification.
  • Validated quickstart. A minimal, copy-paste path that installs the PDF extra, estimates cost, runs a tiny corpus, inspects warnings, and loads CitationGraph.
  • Compatibility. Honest Python/OS support, external service requirements, Docling/OCR caveats, and tested dependency bounds.
  • Release notes. A short CHANGELOG.md with v0.1.0 scope, known limitations, artifact compatibility, and model/pricing date.
Soon after v0.1.0

Important

  • API reference. Generated pages for Pipeline, configuration objects, schemas, CitationGraph, exceptions, and artifact contracts.
  • Troubleshooting. Scanned PDFs, empty bibliographies, rate limits, truncated LLM output, stale caches, dependency installation, and how to resume.
  • Methods & reproducibility. Prompts/model version, dedup scoring, thresholds, stable IDs, provenance manifests, and how to report a run in a paper.
  • Citation. Add CITATION.cff (and eventually a DOI/Zenodo archive) so the target audience can cite the software.
  • Community. CONTRIBUTING.md, support/issue templates, development setup, test strategy, and a small example corpus that is legally redistributable.
Two documentation inconsistencies worth fixing immediately. The quickstart calls Pipeline.run() after the base install even though PDF conversion is an optional extra. Separately, the PipelineResult docstring says papers is indexed by id, while the implemented and documented graph API intentionally keeps id as a column.

Product architecture

Library first, UI beside it

Your intuition is right. The Python library should remain the independent engine and source of truth. The UI should depend on that engine through a small application/service layer—never duplicate algorithms or scrape CLI output.

Interface

Local browser UI

Projects, file selection, progress, review, exploration, exports.

→
Application layer

Jobs + decisions

Run/resume/cancel, progress events, safe file handling, curation records.

→
Independent package

citegraph core

Pipeline stages, schemas, artifact contracts, algorithms, provider adapters.

Recommended shape

A local-first web companion, in the same repository at first.

Publish citegraph independently to PyPI. Add a top-level UI application with its own dependencies and entry point, importing the core package. Run a small local FastAPI backend and open the browser; use a focused JavaScript frontend only where it earns its keep (file/project screens, live progress, table editing, graph exploration). This keeps PDFs on the researcher’s machine except for the already-disclosed calls to Gemini and metadata providers.

Separate package boundaries now; separate repositories later only if deployment, teams, or release cadences actually diverge. Repository separation is not what creates architectural independence—the one-way dependency does.

Core capabilities the UI needs first

  • Structured progress events instead of Rich-only rendering
  • Cancellation and durable job/stage state
  • Stable project IDs, artifact schema versions, and provenance
  • A documented decision/override schema keyed by stable entities
  • Typed service methods returning status/result DTOs—not console strings
  • Clear error categories with actionable, user-safe messages

Boundaries to protect

  • The core must never import FastAPI, browser, or frontend code
  • The UI must not shell out to citegraph or parse terminal output
  • Provider keys stay server-side/local-backend side, never browser storage
  • Every edit becomes a persisted, replayable decision with provenance
  • Users can always export plain artifacts and leave the UI
  • Hosted mode, if added, uses the same application contract
MVP scope

The researcher journey

The first UI should make the current pipeline understandable and recoverable. It does not need to expose every tuning knob or start with a spectacular network visualization.

Create a project

Choose or drag in PDFs, name the corpus, select OCR mode, and see what stays local versus what is sent to external services.

UI 1

Inspect before spending

Show file count, conversion warnings, estimated tokens/cost, model, and a clear “start analysis” confirmation.

UI 2

Run and resume

Stage timeline, per-file progress, failures with retry actions, cancel/resume, and safe recovery after closing the browser.

UI 3

Review what matters

Start with warnings and a small sample, then support metadata edits, missing references, borderline dedup pairs, enrichment misses, and author aliases.

UI 4

Explore and export

Search/filter papers, references, and authors; view top-cited works and citation context; download all CSV/JSON artifacts. Add interactive graph navigation after table exploration is useful.

UI 5
Important product correction to the old roadmap. Do not pause the pipeline inside a synchronous web checkpoint. Long PDF/OCR/LLM runs should be jobs with durable state; the UI observes progress and records decisions. Re-running affected downstream stages can then be explicit, understandable, and recoverable.
Forward plan

A staged path

Finish the public beta before opening a second product front. Then harden just enough core plumbing for a UI, validate the workflow with real researchers, and only later consider hosted infrastructure.

The next three concrete moves

  1. Release-hardening PR: fix CI/Python support, CLI assertions, current pricing, README install flow, and the incorrect PipelineResult docstring.
  2. Real-corpus evaluation: label representative papers/references/dedup pairs, run the maintained smoke script, publish results and limitations.
  3. v0.1.0 beta release: TestPyPI install, trusted publisher check, tag, GitHub release notes, PyPI verification.

Decision to make after release

Interview or observe 3–5 researchers using the CLI-assisted workflow. The key question is not “which frontend framework?” but where they lose confidence or get stuck: installation, cost, waiting, warnings, correction, or exploration.

Use that evidence to write the first UI specification. The architectural recommendation here deliberately leaves visual design and exact endpoint shape open until then.
